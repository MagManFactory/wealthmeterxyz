# Homepage rotation procedure

Owner approved refreshing both homepage leads and repeating on Monday, Wednesday and Friday on 2026-10-16. The parent task manages scheduling; this release creates no scheduler.

1. Read this procedure and data/homepage-rotation-history.json in each production repository. Fetch current origin/main into clean isolated clones. LifeMeter deploys from MagManFactory/lifemeter-xyz; WealthMeter deploys from MagManFactory/wealthmeterxyz. Preserve dirty checkouts, credentials, sharing and unrelated releases. Never force-push.
2. Inspect the current live homepages and existing published /stories/ articles. Select a useful, accurate story per site, varying topic from the current lead. Prefer evergreen stories when a dated claim cannot be freshly verified. Review the complete article and primary-source support; retain the published headline, text, dates, caveats and existing accessible imagery. Skip any questionable story instead of inventing or revising reporting.
3. Avoid repeating any of the last six selected lead URLs where the eligible inventory allows. Use the history as the source of truth, retain at most 24 entries, and record the previous and new title/URL, supporting-card adjustment, date and reason. If there is no suitable different published story, leave that homepage unchanged and report why.
4. Replace only the candidate-lead article in index.html, retaining visual-lead rotated-lead and rotation-image classes. Reuse the selected article photo, alt text, headline, eyebrow and standfirst. Use root-relative /stories/name.html links. If the lead duplicates an opening-side quick-story, replace that one opening card with a different published story. Do not alter hidden menu/search cards, article bodies/dates, feeds, longform queues, Story registry, tool access or monetization.
5. Run content policy, longform order, Phoenix navigation inventory, Longform corpus and Specials checks in each affected repo; run git diff --check. The established build_seo_artifacts.py --write currently rewrites many unrelated files and can remove Phoenix asset references. If run for release compatibility, isolate it, inspect its output, and restore unrelated generated changes before final checks. Homepage-only rotation needs no sitemap/feed regeneration because URLs and article metadata are unchanged.
6. Inspect both homepages at desktop and mobile widths in light and dark themes. Check headline wrapping, image load/alt text, lack of horizontal overflow, lead image/title/CTA destination, and opening-card variety. Check the LifeMeter desktop and mobile WealthMeter links on representative recent and older longform pages. Resolve root-relative links with and without .html and from nested /stories/ and /features/ paths. Verify all changed destinations and assets return HTTP 200.
7. Commit only reviewed homepage files and the rotation ledger. Immediately refetch current main, rebase if required, rerun checks for conflicts, and publish with an ordinary fast-forward push HEAD:main through the established GitHub Pages path. Keep site remotes distinct. Do not publish unreviewed generator churn. Preserve WealthMeter inflation release cb7dada and all later features.
8. Wait for the exact commit's GitHub Pages build/deployment and Content Policy workflow to succeed. Read back live index.html, changed CSS and changed navigation pages; compare SHA256 against the committed bytes. Click the actual rendered lead links and sister-site link. Record deployment URLs, commits, HTTP results and layout evidence. On failure, stop this site's rotation and report the exact blocker. Roll back only via a scoped revert on current main, never by resetting or force-pushing.
